## Root cause and fix

The break-window creation path calls SetWindowPos before it creates the reminder's child controls. Windows synchronously sends WM_SIZE; breakProc calls layoutBreak, which used to build a deferred-position batch containing null child HWNDs. The failed deferred-position batch was the cause of the observed per-window USER-object growth.

The candidate fix in src/app.cpp returns from layoutBreak until the break window and its required title and completion controls exist. The later layout call runs after child creation. This prevents the invalid initial batch while retaining the normal layout and existing window/font cleanup.

Historical evidence supplied for this task reports 110 cycles and 240 samples on v1.2.0, with USER objects increasing from 155 to 373 (+218, approximately +2 per break window). The candidate's earlier 12-cycle regression was also reported as passing. These are historical observations, not new measurements from this verification attempt.
