## Finding

The original v1.2.0 USER-object leak was independently reproduced with the exact published executable. In matched 110-cycle scheduled tests, it added 222 USER objects on both Windows Server 2025 x64 and Windows 11 ARM64 under x64 emulation. The v1.2.1 candidate added zero across the same cycle count and stayed within the measured idle counter noise. A separate 220-cycle accelerated Win32 window-lifecycle regression reproduced approximately two USER objects per cycle in v1.2.0 and showed no growth in v1.2.1.

The candidate passed the current core, binary/package, GUI, installer, 220-cycle and scheduled-soak checks. The tests support fixing the reported USER-object leak; they do not establish native x64 Windows 11 compatibility. Windows 11 ARM64 results are explicitly x64 emulation.

## Root cause and code change

`showBreak` resizes the break window before creating its child controls. Windows synchronously sends `WM_SIZE`; the old `layoutBreak` then attempted a deferred-position batch with null child window handles. The batch failed and left a USER object behind for each reminder lifecycle.

In `src/app.cpp`, `layoutBreak` now returns until the break window and its title and completion controls exist. The normal layout runs after control creation. The fix addresses the invalid early positioning call; it does not retain old windows or hide the resource count. No product source changes followed the fix commit in the tested build tree (`git diff 7adc754..8a738c1 -- src` was empty).

## Comparative scheduled soak

The reusable PowerShell harness used the application’s real one-minute work interval and 30-second break interval. It did not alter production defaults. Each run completed 110 scheduled cycles, created 116 break windows (three cycles each included two snoozes), and ran for about 2 hours 6–7 minutes. It exercised 22 Skip, 22 Complete, 22 Escape, 22 close, 19 natural-completion cycles, and three double-snooze-then-Skip cycles. It changed themes every 20 cycles, paused/resumed every 25 cycles, sampled resources and timer/window state throughout, then restarted the owned application during an active break. The restart check required a fresh Running work state, no reopened break window, and unchanged settings hash.

The USER summary uses the median of the first five and last five post-close cycle samples and a least-squares slope over all 110 post-close samples. A 12-sample idle baseline measured the counter noise. The candidate threshold is that start-to-end drift remain within the measured idle range plus one USER object; the baseline threshold requires at least half the historically observed approximately two-object-per-cycle slope and drift. The exact CSVs and raw JSON used for these calculations are retained below.

### Other resources

The soak recorded GDI objects, process handles, private bytes, working set, cumulative process CPU time, top-level windows, break-window count, timer state/countdown and notification setting in every time-series row. Handles remained flat or declined slightly. Working set declined during all four runs. Mean process CPU calculated across adjacent same-PID samples was 0.41% on Server and 1.08% under ARM64 emulation; PID changes at the restart probe were excluded from CPU deltas.

GDI counts had short-lived increases while reminder windows were open. The after-close candidate range was 56–60 on Server and 56–62 on ARM64. On ARM64, both versions showed the same bounded after-close level changes (56, then 59, 60, and 61 at later theme-transition regions); the levels stayed flat within long stretches between those transitions. The v1.2.0 ARM64 baseline had the same pattern and +5 end-median difference as v1.2.1. This points to bounded common-control/theme or OS resource accounting rather than a candidate-specific per-reminder leak; its exact source was not isolated. It did not show a per-cycle GDI rise like the v1.2.0 USER-object defect.

Private-byte first/last-five medians rose modestly during some runs: Server v1.2.0 3.53→4.13 MiB, v1.2.1 3.51→4.18 MiB; ARM64 v1.2.0 15.71→16.03 MiB, v1.2.1 15.70→15.78 MiB. The detailed 10-cycle medians show step changes and plateaus, rather than continuing growth at the USER-object rate. The candidate remained below 4.2 MiB private bytes on Server; no crash, hang, handle escalation, or accumulating break window was observed. This soak does not prove that all small heap growth is absent; the measured private-byte movement is retained for comparison rather than being called zero.

## Harness corrections and intermediate attempt

The initial long-soak harness had several test-only problems that were corrected before the successful full run: a case-insensitive variable/parameter name collision, malformed PowerShell filter expressions, a CRLF settings fixture incompatible with the app's raw settings parser, and Escape input sent without confirmed foreground focus. The current harness verifies the foreground window first. Where GitHub's Windows 11 ARM runner could not grant foreground focus, the test records Escape as **NOT TESTED** and closes the reminder through Skip; a confirmed-focus Escape failure would remain **FAIL** and fail the run. The final Windows Server run delivered Escape successfully in all 22 cycles per version. An earlier partial ARM attempt stopped at cycle 3 on the focus problem and is not counted as a completed test or as a product failure.

The regression threshold is based on the 12 idle samples and the original observed approximately +2 objects per reminder; it was not relaxed to make the candidate pass. The published binary still fails this test, which confirms the test can detect the original defect.

## Remaining limitations

The following were not established by this hotfix run:

- Native x64 Windows 11: no isolated x64 Windows 11 VM/runner was available. The Windows 11 results above ran the downloaded x64 executable under ARM64 emulation; Windows Server results were native x64.
- Escape keyboard delivery on the Windows 11 ARM64 runner: 22 cycles per version were NOT TESTED because foreground focus was unavailable. Equivalent Escape dismissal was directly verified on the native x64 Windows Server runs.
- The 12 NOT TESTED observations in candidate installer acceptance remain separate from the soak results: Narrator speech; close-to-tray TaskDialog instruction text via native controls; separate Windows Shell notification surface; production/physical audio playback; candidate and v1.1.0 uninstall finish-page Run checkbox state; candidate and v1.1.0 extracted NSIS UI-process exit codes; real lock/unlock; physical sleep/resume; multiple-monitor configuration/restoration; physical speaker output. Interactive uninstall completion itself passed: the parent exited with code 0 and executable, install directory, shortcuts and registry entries were removed. The extracted UI process exit code was unavailable after process exit, so it is not claimed.
- The soak deliberately disables alarms and notifications in its isolated profile; the GUI/installer suites cover application behavior, but this soak does not validate a physical audio endpoint or visible Windows toast.
- GDI counts show small bounded theme/OS-linked changes under ARM64 emulation; there is no continuing per-cycle pattern and the baseline shows the same levels. The exact system cache/accounting source was not isolated.
- Private bytes increased modestly by sub-megabyte amounts over some two-hour runs and reached plateaus; the data is included and no broader heap-leak claim is made.

These limitations do not invalidate the USER-object fix evidence. They remain relevant when describing platform and hardware-specific coverage.
