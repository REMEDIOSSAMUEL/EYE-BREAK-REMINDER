## Network and release trust

- Production API and asset requests use native WinHTTP and HTTPS with normal Windows certificate-chain and hostname validation. Production certificate validation is never disabled.
- The API hostname is fixed to `api.github.com`; the release URL, repository path, tag and exact asset name are validated against `REMEDIOSSAMUEL/EYE-BREAK-REMINDER`.
- Asset downloads begin only at the canonical `https://github.com/REMEDIOSSAMUEL/EYE-BREAK-REMINDER/releases/download/<tag>/<asset>` URL. Automatic redirects are disabled. Each redirect is checked and limited to HTTPS on port 443 at `github.com`, `release-assets.githubusercontent.com`, `objects.githubusercontent.com`, or `github-releases.githubusercontent.com`; there are at most five redirects.
- Drafts, prereleases, malformed versions, older/equal versions, duplicate/missing assets, unsupported sizes and malformed SHA-256 metadata are rejected. The supported asset size limit is 100 MiB.
- The updater streams bytes to a uniquely created `.part` file, checks available disk space, verifies the exact declared size and GitHub API SHA-256 digest using Windows CNG, flushes the file, and only then atomically renames it into verified staging. A second SHA-256 and version check occurs immediately before execution/use.
- The setup is launched with a fixed `/S` argument and an explicit executable path after transaction validation. Portable replacement targets one fixed filename. No URL, path, or installer argument is assembled from user-controlled release notes.
- Per-request WinHTTP connection/request handles and CNG handles use scoped owners. A bounded process-lifetime WinHTTP session cache (maximum eight configurations; two production timeout profiles) avoids the process-handle growth observed when opening a fresh session for each failed DNS request. Proxy and timeout settings are part of the cache key; Windows reclaims the fixed session set at process exit. API and download calls have connect/send/receive timeouts; downloads also have a ten-minute total limit and responsive cancellation between reads. Failure to configure a bounded download timeout or disable WinHTTP automatic redirects is fatal: the updater sends no request and removes the partial staging file.

## Signed update manifest policy

The production update path now requires `EyeBreakReminder-UpdateManifest.json` and `EyeBreakReminder-UpdateManifest.sig`. The exact canonical manifest bytes are verified with Windows CNG ECDSA P-256/SHA-256 against a public key compiled into the app. It binds the official app/repository, stable version, channel, x64 architecture, exact installer and portable roles, sizes and SHA-256 digests. Verification happens before update offers and again at the coordinator execution boundary. The download size and signed SHA-256 are checked before use. Invalid, missing, stale, modified, mismatched, or unknown-key metadata has no unsigned fallback.

`src/update_trust.hpp` deliberately contains no production key yet. `ProductionUpdateKeyProvisioned` is false. Until the owner generates a protected offline key and embeds its public half, the production app rejects all update offers. No production private key exists in the checkout or artifacts. Automated test roots are confined to `EYEBREAK_TEST_BUILD` and are not trusted by production builds.

The local offline signer is also guarded: it rejects private-key paths inside the checkout, discovered/configured OneDrive roots, and the system temporary directory. Windows generation requires a new dedicated key directory, removes inherited ACL entries, grants only the current user's SID full control, then checks that the private file inherited that DACL. The PEM is passphrase-encrypted with AES-256-CBC. These safeguards do not replace the required encrypted offline backup. The current environment had no existing Eye Break Reminder production key/certificate and no removable backup volume, so no production identity was generated or embedded.

GitHub HTTPS and its digest remain useful transport/integrity checks but do not independently authenticate the publisher. The signed manifest adds that update-channel authentication only after the trusted v1.4.0 bootstrap. It is not Windows Authenticode, does not establish a Windows publisher name, and does not promise to remove SmartScreen warnings. The original Authenticode requirement remains a separate unresolved acceptance gate. The owner must explicitly approve the proposed signed-manifest alternative release policy before publication.

The stalled-body timeout harness has a narrowly scoped test-only exception: when `EYEBREAK_TEST_BUILD` is defined, the downloader accepts a dynamic HTTPS port only for the exact host `localhost`, uses a direct proxy-free session and short timeouts, and honors `EBR_TEST_ALLOW_UNTRUSTED_LOOPBACK_CERT=1` only for that parsed loopback request. It sets only `SECURITY_FLAG_IGNORE_UNKNOWN_CA`; certificate name, date, and server-usage checks remain enabled. The self-signed certificate has a `localhost` SAN, and the harness does not modify any Windows certificate store. This test exercises the real `downloadVerified` WinHTTP body timeout, not production certificate trust. Separate production-policy and exact-candidate tests verify rejection of untrusted certificates and unsafe hosts. Production builds do not define the test macro, and the test-only flag branch is absent from them. The native child is bounded to 15 seconds and the workflow step to five minutes.

## Local files, backups and recovery

The downloader creates a new GUID directory under the app's known data root, rejects directory/file reparse points in the paths it manages, and writes fixed allowlisted filenames. The coordinator validates canonical paths, current per-user installation registration, transaction fields, prior and candidate versions, digests, file sizes and profile identity. It backs up only the three exact settings/timer/history files and the four named files owned by the NSIS install; clean reset/uninstall still targets only exact known data files. It does not recursively delete AppData or portable folders.

The HKCU RunOnce entry points only to the copied coordinator inside the validated transaction folder and is created before installation. It is removed after a complete journal or successful rollback. If rollback cannot safely finish, previous files and settings backups remain staged and the error is shown. The application does not upload settings/history, send telemetry, or include credentials in the update request.

## Same-account local access boundary

The updater is designed for a normal per-user Windows installation and is not a defense against a malicious process already running with the same user account. Update staging and transaction files inherit the profile's ACLs, and a same-account process can already alter that user's application files and data. The portable updater also relies on a fixed executable filename in a validated directory; it does not claim a security boundary against same-user modification of that directory.

The coordinator rechecks the staged installer digest at the execution boundary, and hosted tests reject a replacement performed before that check. Recovery backups also carry SHA-256 digests in the transaction journal: creation compares the source and copied bytes, and restore validates all backups and temporary restore copies before applying any live-file changes. A missing or corrupted later backup is rejected without partially replacing earlier settings/history files. These digests detect corruption and incomplete copies; they do not authenticate the journal against a process running as the same user. Neither mechanism eliminates or tests a same-user time-of-check/time-of-use race in the narrow interval between hashing and process creation. Do not claim protection from active same-user malware or absolute immunity to local file races. This is a documented threat-model limit; it does not resolve the separate release blocker that the publisher trust root is not provisioned and the candidate is unsigned.
