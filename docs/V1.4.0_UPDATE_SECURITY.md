# v1.4.0 updater security model

Status: implementation security notes. Do not describe this unsigned updater as publisher-signed or Authenticode-verified.

## Network and release trust

- API and asset requests use native WinHTTP and HTTPS with the normal Windows certificate chain and hostname validation. Certificate validation is never disabled.
- The API hostname is fixed to `api.github.com`; the release URL, repository path, tag and exact asset name are validated against `REMEDIOSSAMUEL/EYE-BREAK-REMINDER`.
- Asset downloads begin only at the canonical `https://github.com/REMEDIOSSAMUEL/EYE-BREAK-REMINDER/releases/download/<tag>/<asset>` URL. Automatic redirects are disabled. Each redirect is checked and limited to HTTPS on port 443 at `github.com`, `release-assets.githubusercontent.com`, `objects.githubusercontent.com`, or `github-releases.githubusercontent.com`; there are at most five redirects.
- Drafts, prereleases, malformed versions, older/equal versions, duplicate/missing assets, unsupported sizes and malformed SHA-256 metadata are rejected. The supported asset size limit is 100 MiB.
- The updater streams bytes to a uniquely created `.part` file, checks available disk space, verifies the exact declared size and GitHub API SHA-256 digest using Windows CNG, flushes the file, and only then atomically renames it into verified staging. A second SHA-256 and version check occurs immediately before execution/use.
- The setup is launched with a fixed `/S` argument and an explicit executable path after transaction validation. Portable replacement targets one fixed filename. No URL, path, or installer argument is assembled from user-controlled release notes.
- WinHTTP and CNG handles are closed by scoped owners. API and download calls have connect/send/receive timeouts; downloads also have a ten-minute total limit and responsive cancellation between reads. Failure to configure a bounded download timeout or disable WinHTTP automatic redirects is fatal: the updater sends no request and removes the partial staging file.

## Publisher-authentication limitation

GitHub's HTTPS connection and asset digest protect transport and detect incomplete or altered downloads relative to the digest returned by GitHub. They do not independently prove that a release was authored by the intended maintainer if the GitHub repository/account, release metadata, or GitHub asset service is compromised. The repository currently has no configured release-signing key, signed update manifest, or trusted Authenticode certificate. No private key is embedded, requested, generated for production, or committed. Artifacts remain unsigned, and normal Windows SmartScreen/security warnings remain enabled.

A future signed-manifest design needs a protected signing-key lifecycle and CI secret provisioning. A certificate, private key, release secret, or policy exception must be supplied by the repository owner; this implementation does not pretend the current release is signed. Authenticode support should use Windows trust APIs if a legitimate publisher certificate becomes available.

The Windows acceptance harness has one test-only exception: when `EYEBREAK_TEST_BUILD` is defined, the downloader accepts a dynamically assigned HTTPS port on the exact host `localhost`, uses a direct proxy-free session, and applies shorter connection/read timeouts to reach the disposable loopback server deterministically. The hosted test temporarily trusts a unique public-only localhost certificate in that runner user's Root store, uses normal WinHTTP certificate/hostname checks, and removes the certificate afterward. The test process has a 60-second limit and its workflow step a three-minute limit. Production builds do not define this macro; a separate production-policy test confirms localhost, non-443 ports, plaintext HTTP, URL credentials and hostname lookalikes are rejected.

## Local files, backups and recovery

The downloader creates a new GUID directory under the app's known data root, rejects directory/file reparse points in the paths it manages, and writes fixed allowlisted filenames. The coordinator validates canonical paths, current per-user installation registration, transaction fields, prior and candidate versions, digests, file sizes and profile identity. It backs up only the three exact settings/timer/history files and the four named files owned by the NSIS install; clean reset/uninstall still targets only exact known data files. It does not recursively delete AppData or portable folders.

The HKCU RunOnce entry points only to the copied coordinator inside the validated transaction folder and is created before installation. It is removed after a complete journal or successful rollback. If rollback cannot safely finish, previous files and settings backups remain staged and the error is shown. The application does not upload settings/history, send telemetry, or include credentials in the update request.

## Remaining limits to test

Publisher authentication is limited to HTTPS plus GitHub's unsigned asset digest. RunOnce execution can be restricted by managed Windows policy; if registration cannot be created, installation is stopped before the installer runs. Recovery still depends on Windows allowing the user-level helper to execute and the target folder to be writable. Hosted acceptance must exercise install failure, failed startup, cancellation, hash mismatch, standard-user install and portable replacement before any publication approval.
