## Trust model

GitHub HTTPS protects the connection to GitHub, and a GitHub-provided SHA-256 digest detects payload corruption relative to the release metadata returned by GitHub. If the repository, release account, or publication metadata is compromised, those values can be changed together. They do not independently establish maintainer authorization.

The production updater therefore requires an ECDSA P-256/SHA-256 signed update manifest. The embedded production verification key ID is `p256-0aff97759ea95258`. The owner confirmed an encrypted private-key backup in a password manager. The required status is: “Encrypted production private-key backup confirmed by the owner. Independent backup restoration was not performed.” Signing and recovery details are in [UPDATE_SIGNING_AND_KEY_MANAGEMENT.md](UPDATE_SIGNING_AND_KEY_MANAGEMENT.md).

## Network and release validation

- Release discovery uses native WinHTTP against the fixed GitHub API host and official repository.
- Drafts, prereleases, malformed or non-newer versions, unsupported assets, duplicate assets, and malformed sizes or digests are rejected.
- Asset URLs must match the official release path. Automatic redirects are disabled; each redirect is validated, limited to HTTPS on port 443, restricted to approved GitHub asset hosts, and limited in number.
- Downloads stream to uniquely created `.part` files. The updater validates available space, exact byte count, GitHub digest consistency, and the publisher-signed SHA-256 before atomically moving a payload into staging.
- WinHTTP sessions, request handles, CNG handles, download timeouts, cancellation, and temporary files have bounded lifecycle behavior. Failure to establish required request policy is fail-closed.

## Signed update manifest

Production requires `EyeBreakReminder-UpdateManifest.json` and `EyeBreakReminder-UpdateManifest.sig`. The exact canonical manifest bytes are verified using Windows CNG ECDSA P-256/SHA-256 and the public key embedded in the application. The manifest binds the application and repository identities, stable version, channel, x64 architecture, signing key ID, issue/expiry times, and exactly two payload roles: the installed setup executable and the portable-update executable. Each payload entry binds its filename, role, installation type, architecture, size, and SHA-256 digest.

Verification happens before an update is offered and again at the coordinator execution boundary. The selected payload is checked for size and digest before execution or replacement. Missing, malformed, expired, modified, wrong-key, wrong-identity, wrong-version, wrong-architecture, wrong-role, replayed, or downgraded metadata is rejected. There is no unsigned-update fallback and no ordinary-user signature bypass.

The initial v1.4.0 installer is a bootstrap boundary: an embedded key cannot authenticate the installer that first delivers it. Under the owner-approved policy, the initial installer may be unsigned; obtain it through a trusted manual process and independently verify its provenance and checksum. The signed manifest authenticates later updates only.

## Transaction safety and recovery

The updater stages fixed allowlisted names in a GUID directory under the application data root. It validates canonical paths, per-user installation registration, transaction fields, current and target versions, signed payload identity, and the profile location. The coordinator revalidates signed metadata and payload identity before installation.

Recovery records identify the prior executable, exact application-owned files, and known settings/timer/history files. Backups and restore copies are hashed before use. Installation or relaunch failure restores the prior executable and only the recognized data and registration state. If safe recovery cannot finish, the backup and recovery registration remain available and the failure is reported. The updater does not recursively delete the shared application-data folder or unrelated portable files.

Invalid update metadata or payloads must leave the installed application, settings, history, registry state, and unrelated files unchanged, and must not launch the installer. Current acceptance classifications and exact evidence identities are maintained in [V1.4.0_ACCEPTANCE_MATRIX.json](V1.4.0_ACCEPTANCE_MATRIX.json) and the final verification report.

## Test and production separation

Production builds trust only the public key in `src/update_trust.hpp`. They cannot load a test key from an environment variable, command line, test fixture, or release asset. Test signing support and local feed/data overrides are compiled only into `EYBREAK_TEST_BUILD`. Test private keys are ephemeral and are never production roots.

## Authenticode and threat-model limits

A signed update manifest does not Authenticode-sign the EXE or installer, establish a Windows publisher name, or guarantee removal of SmartScreen warnings. The owner approved Authenticode as optional for v1.4.0; the initial installer may remain unsigned if clearly disclosed. SignPath approval is not required by the approved policy. Findings and application prerequisites are documented in the signing and key-management guide.

The updater targets a normal per-user Windows installation. It is not a defense against malicious code already running as the same Windows user. File hashes detect corruption and incomplete copies; they do not authenticate the local transaction journal against a same-user process or eliminate every same-user time-of-check/time-of-use race.
