# v1.4.0 updater test plan

Status: required acceptance matrix. Record PASS only with exact build/run evidence; use NOT TESTED for unavailable UI, hardware or infrastructure.

## Deterministic/core checks

- Semantic versions: `1.3.0 < 1.4.0`, equality, `1.4.1 > 1.4.0`, and `1.10.0 > 1.9.9`; missing, malformed, prefixed and prerelease tags.
- GitHub response: official repository/release URL, stable-only policy, size limits, exact setup/portable asset selection, duplicate/missing assets, unsupported formats, bad/missing digest and unrelated URLs.
- Settings: old profile migration, unknown valid legacy-key retention, update-preference defaults/persistence, history retention, clean reset policy and schema-validation recovery.
- Windows unit harness: test-only fixture streaming/progress, short-stream interruption cleanup, cancellation, deliberate digest mismatch, unsafe host/filename rejection, second-process named-mutex coordinator exclusion/retry, strict transaction-record round-trip/duplicate-field rejection, and injected `WinHttpSetTimeouts`/redirect-lockdown setup failures that must fail closed before data is received (`make updater-windows-test`).
- Hosted TLS fault injection: the test build alone can route official GitHub release-asset downloads through an isolated loopback HTTP CONNECT proxy. The proxy accepts only port 443 connections to the allowlisted GitHub release hosts and tunnels TLS unchanged, so WinHTTP performs normal certificate and hostname validation end-to-end against GitHub. It resets the first asset connection after forwarding encrypted response bytes, without changing the trust store or decrypting traffic. The updater must reject and delete partial bytes while preserving an install sentinel, then retry the actual public asset and verify its size, byte progress and GitHub SHA-256 digest. The test proxy setting exists only in `EYEBREAK_TEST_BUILD`; production networking and trust behavior are unchanged.
- Build/package: production app, GUI-test app, setup, portable ZIP, source ZIP and SHA-256 manifest; verify installer/app version metadata and dependency/import assertions.

## Real public GitHub smoke

Run `make github-updater-smoke` against the actual public repository. It uses the production WinHTTP API/download implementation without credentials, discovers the latest stable release, confirms the 1.4.0 development version is newer than the published stable version, selects both supported Windows assets, downloads them to a new isolated `build/` folder, records true byte progress, and checks exact size and digest. It never executes the downloaded v1.3.0 files. Keep this evidence separate from local future-release fixtures.

## Hosted disposable Windows acceptance

The hosted Windows runner must use its disposable per-user profile and actual compiled binaries/installer. Do not run installer/data-deletion tests in the developer's Windows profile.

1. Fresh installed setup, registration/shortcuts, settings path and standard-user operation.
2. Download and verify the actual public v1.3.0 setup, install it to a disposable per-user path, install the v1.4.0 candidate in place, start the new executable with legacy settings, verify history and settings, then uninstall.
3. v1.4.0 test build discovers a local fixture future release and installs the exact test setup; verify download progress, hash/size, shutdown, NSIS installer, relaunch, running version and preserved data.
4. Run the exact release-candidate app and setup in a separate disposable installation. Build a v1.4.1 successor from production updater code with only Windows version resources changed, then serve its release JSON and setup bytes over a temporary TLS endpoint using the exact official GitHub hostnames. Before trusting the test CA, make Windows and the installed production binary reject its certificate; verify the production UI reports the secure-connection error, no HTTP metadata request reaches the feed, no staging/coordinator or executable change occurs, and history/unrelated data remain byte-identical. Then briefly map those names to loopback and install the one-runner test CA in CurrentUser Root; drive the candidate's normal discovery, accessible update dialog, real WinHTTP transfer, GitHub SHA-256 check, coordinator, NSIS update and relaunch. Verify the new process/path/hash/file version/Installed Apps version, every seeded setting value, history bytes, staging cleanup and untouched unrelated profile data. The harness restores the hosts file byte-for-byte, removes the test root and all private keys, and uploads no keys. This verifies the exact production updater path in a controlled environment but does not establish production publisher authenticity; the temporary CA is test trust only.
5. The controlled successor build and feed use a newer 1.4.1 test executable built from production updater code with only version resources changed. The expected last-check timestamp may advance during the real production update; compare all other persisted setting keys and values, and compare history/unrelated sentinels byte-for-byte. Record final run outcomes and exact hashes in the acceptance matrix and final verification report.
6. Clean install resets settings/custom accents/startup but preserves history unless its separate checkbox is selected; explicit confirmation and cleanup stay within the isolated test profile.
7. Cancel a slowed fixture copy; verify the old app/data remain and no coordinator starts. Separately run the hosted TLS fault-injection case above: terminate a real HTTPS response mid-body, verify partial staging is removed and the installed-app sentinel remains byte-identical, then retry on a new HTTPS connection and verify full progress and SHA-256. A corrupt fixture with a valid declared size but wrong digest must be rejected before execution.
8. Controlled installer exit failure and failed-new-start scenarios restore the prior executable, NSIS-owned files, registration and data. The hosted acceptance also pauses a test build after clean settings removal, terminates only that disposable coordinator, verifies the exact per-user RunOnce command, replays its recovery command, and checks executable/settings/history/startup restoration. This tests interrupted-transaction recovery without rebooting the hosted runner; an actual OS reboot and automatic next-sign-in launch remain NOT TESTED.
9. Portable copy installs a future standalone executable without registering an installed app, replaces only its own executable, relaunches, and retains nearby unrelated files. Also run portable Clean Install with history retained and with separately confirmed history deletion; verify default timer/theme/colour/schedule/update preferences, history file bytes or exact deletion, unrelated nearby files and absence of an Installed Apps registration. Exercise an unwritable portable directory, a locked portable executable, and a failed post-replacement startup using versioned disposable executables under `RUNNER_TEMP`; verify the exact old executable hash/version, settings/history, unrelated files, durable recovery registration, recovery cleanup and relaunch. These tests must stop at their fail-closed environment guard on developer machines.
10. Open Windows Settings > Installed apps and verify the updated app entry/version when that UI is exposed. Then test interactive uninstall Keep/Remove choices, silent uninstall's keep policy, reinstall after uninstall, and uninstall after an automatic, clean, or recovered update. Verify the uninstall registration and exact retained/deleted data files; record Settings UI as NOT TESTED if that host does not expose its UI.
11. Repeated install attempts cannot create a second coordinator. Verify the timer advances during a deliberately slowed update download and automatic update prompts wait until an active break ends, then appear immediately after the user ends the break without waiting for another work interval. Timer work, paused state, tray-hidden shutdown and pending audio/reminder lifecycles remain correct.
12. Dark, Light, both High Contrast themes, Follow Windows Theme, Forced Colors, custom accents, keyboard navigation, focus, text scaling, screen-reader control names, progress/error/status and Cancel.
13. USER/GDI/thread/handle/private-byte/working-set/CPU traces during the established 110-cycle reminder soak. At cycle 0/1/every tenth cycle also sample child processes, TCP connections and updater staging-file counts. Inspect the complete series and report unavailable measurements separately. Bind the soak to the exact candidate executable SHA-256. Separately monitor repeated update-dialog creation, update checks, cancelled/failed downloads, successful digest verification and updater-helper launches; the reminder-cycle soak alone does not cover these updater resource scenarios.

## Bounded download and recovery probes

- Use an ephemeral hosted Windows runner and a unique `RUNNER_TEMP` directory for the HTTPS response-body stall test. A disposable test CA is installed only in the runner's CurrentUser Root store, the loopback server sends valid HTTPS HTTP 200 headers with a declared body and then withholds every body byte, and the actual production `downloadVerified` function must return a timeout error within its configured bound. Verify no partial or final payload remains, an existing-data sentinel is unchanged, the test child process is bounded, the temporary CA is removed, and the staging directory is deleted. The test is not a production endpoint override and must fail closed outside GitHub Actions.
- The real HTTPS interruption test and stalled-body timeout test are separate cases: reset a real official asset transfer to prove partial-file deletion/retry, then hold a trusted loopback TLS response open to prove a body-read timeout. Do not substitute an offline unit test for either transaction.
- After a harness failure, preserve its exact log and classify whether execution reached the server, sent response headers, and withheld the body. A harness timeout without phase/feed evidence is not proof of a product timeout defect. Bound native test children and record the feed state so a stalled test cannot consume the workflow's full timeout without a diagnostic.
- Recovery checks validate the complete backup set before modifying any live data. Corrupt or missing settings/history/installer-owned backups must be rejected before any earlier file is partially restored. Compare actual file bytes and executable identity; the presence of a backup file alone is not proof of rollback.

## Candidate identity and evidence

Build one authoritative v1.4.0 candidate after production code freezes. Capture source commit, compiler/NSIS versions, runner image, five release filenames, sizes and SHA-256 values. Run final package, installed-upgrade, GUI, installer, update and resource assertions against those exact files. Download the retained Actions artifact independently and verify the manifest and candidate hashes. A code change after candidate testing requires a new candidate and affected acceptance reruns; documentation-only edits do not.

The feature workflow builds temporary v1.4.1 test metadata/installers only inside a disposable Windows runner. It never publishes or tags those fixtures. The downloaded v1.3.0 setup is byte-verified through the updater's public GitHub smoke path before the first-transition test uses it.
