# v1.4.0 updater test plan

Status: required acceptance matrix. Record PASS only with exact build/run evidence; use NOT TESTED for unavailable UI, hardware or infrastructure.

## Deterministic/core checks

- Semantic versions: `1.3.0 < 1.4.0`, equality, `1.4.1 > 1.4.0`, and `1.10.0 > 1.9.9`; missing, malformed, prefixed and prerelease tags.
- GitHub response: official repository/release URL, stable-only policy, size limits, exact setup/portable asset selection, duplicate/missing assets, unsupported formats, bad/missing digest and unrelated URLs.
- Settings: old profile migration, unknown valid legacy-key retention, update-preference defaults/persistence, history retention, clean reset policy and schema-validation recovery.
- Windows unit harness: test-only fixture streaming/progress, short-stream interruption cleanup, cancellation, deliberate digest mismatch, unsafe host/filename rejection, duplicate-coordinator exclusion/retry, and strict transaction-record round-trip/duplicate-field rejection (`make updater-windows-test`).
- Hosted TLS fault injection: the test build alone accepts a dynamic-port `localhost` HTTPS endpoint, with WinHTTP's normal certificate and hostname validation enabled. A unique short-lived server certificate is trusted only in the disposable runner's CurrentUser store and removed afterward. The server sends an HTTP response body and resets its TLS/TCP connection partway through; the application must reject and delete partial bytes while preserving an install sentinel, then a fresh HTTPS request must complete with progress and a matching CNG SHA-256 digest. This exercises the real `downloadVerified` WinHTTP code rather than the local-copy fixture.
- Build/package: production app, GUI-test app, setup, portable ZIP, source ZIP and SHA-256 manifest; verify installer/app version metadata and dependency/import assertions.

## Real public GitHub smoke

Run `make github-updater-smoke` against the actual public repository. It uses the production WinHTTP API/download implementation without credentials, discovers the latest stable release, confirms the 1.4.0 development version is newer than the published stable version, selects both supported Windows assets, downloads them to a new isolated `build/` folder, records true byte progress, and checks exact size and digest. It never executes the downloaded v1.3.0 files. Keep this evidence separate from local future-release fixtures.

## Hosted disposable Windows acceptance

The hosted Windows runner must use its disposable per-user profile and actual compiled binaries/installer. Do not run installer/data-deletion tests in the developer's Windows profile.

1. Fresh installed setup, registration/shortcuts, settings path and standard-user operation.
2. Download and verify the actual public v1.3.0 setup, install it to a disposable per-user path, install the v1.4.0 candidate in place, start the new executable with legacy settings, verify history and settings, then uninstall.
3. v1.4.0 test build discovers a local fixture future release and installs the exact test setup; verify download progress, hash/size, shutdown, NSIS installer, relaunch, running version and preserved data.
4. Clean install resets settings/custom accents/startup but preserves history unless its separate checkbox is selected; explicit confirmation and cleanup stay within the isolated test profile.
5. Cancel a slowed fixture copy; verify the old app/data remain and no coordinator starts. Separately run the hosted TLS fault-injection case above: terminate a real HTTPS response mid-body, verify partial staging is removed and the installed-app sentinel remains byte-identical, then retry on a new HTTPS connection and verify full progress and SHA-256. A corrupt fixture with a valid declared size but wrong digest must be rejected before execution.
6. Controlled installer exit failure and failed-new-start scenarios restore the prior executable, NSIS-owned files, registration and data. The hosted acceptance also pauses a test build after clean settings removal, terminates only that disposable coordinator, verifies the exact per-user RunOnce command, replays its recovery command, and checks executable/settings/history/startup restoration. This tests interrupted-transaction recovery without rebooting the hosted runner; an actual OS reboot and automatic next-sign-in launch remain NOT TESTED.
7. Portable copy installs a future standalone executable without registering an installed app, replaces only its own executable, relaunches, and retains nearby unrelated files.
8. Open Windows Settings > Installed apps and verify the updated app entry/version when that UI is exposed. Then test interactive uninstall Keep/Remove choices, silent uninstall's keep policy, reinstall after uninstall, and uninstall after an automatic, clean, or recovered update. Verify the uninstall registration and exact retained/deleted data files; record Settings UI as NOT TESTED if that host does not expose its UI.
9. Repeated install attempts cannot create a second coordinator. Verify the timer advances during a deliberately slowed update download and automatic update prompts wait until an active break ends. Timer work, paused state, tray-hidden shutdown and pending audio/reminder lifecycles remain correct.
10. Dark, Light, both High Contrast themes, Follow Windows Theme, Forced Colors, custom accents, keyboard navigation, focus, text scaling, screen-reader control names, progress/error/status and Cancel.
11. USER/GDI/process-handle/private-byte/resource trends during update dialogs, cancellations and errors, plus the established 110-cycle reminder soak when production process lifetimes changed.

## Candidate identity and evidence

Build one authoritative v1.4.0 candidate after production code freezes. Capture source commit, compiler/NSIS versions, runner image, five release filenames, sizes and SHA-256 values. Run final package, installed-upgrade, GUI, installer, update and resource assertions against those exact files. Download the retained Actions artifact independently and verify the manifest and candidate hashes. A code change after candidate testing requires a new candidate and affected acceptance reruns; documentation-only edits do not.

The feature workflow builds temporary v1.4.1 test metadata/installers only inside a disposable Windows runner. It never publishes or tags those fixtures. The downloaded v1.3.0 setup is byte-verified through the updater's public GitHub smoke path before the first-transition test uses it.
