The verifier allows a creation timestamp up to five minutes ahead, requires expiry strictly after issue time and caps the period at 90 days.

- **Successor installation:** the offered successor's own manifest must remain valid during discovery and when installation is authorized. Expiry can reject an old legitimate offer, including after download before handoff. v1.4.0's manifest does not set the expiry for future versions.
- **Rollback:** authenticated recovery can validate a previously authorized transaction after expiry. Signature, identity, version, maximum duration and recovery-state validations still apply. Expiry alone does not stop an otherwise valid rollback.
- **Discovery:** the app evaluates the GitHub release and authenticates metadata when it identifies a newer version. A v1.4.0 app seeing latest v1.4.0 follows the current-version path without validating its expired manifest. A compatible older signed updater seeing an expired newer offer reports verification failure. v1.3.0's check-only flow can still point to the release.
- **Fresh/manual installation:** setup and manual portable use do not evaluate manifest expiry. The initial Windows installer uses the manual bootstrap trust model.
- If the window becomes unsuitable before publishing, retain the existing binaries and package files, obtain signing authorization, and renew the manifest and signature with the existing production key. Record new metadata digests and independently repeat the affected checks. Never extend expiry without a valid replacement signature.
