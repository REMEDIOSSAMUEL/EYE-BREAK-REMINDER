## Install and data layout

- Per-user NSIS installation: `%LOCALAPPDATA%\Programs\EyeBreakReminder`.
- Per-user Windows registration: `HKCU\Software\EyeBreakReminder` and `HKCU\Software\Microsoft\Windows\CurrentVersion\Uninstall\EyeBreakReminder`.
- Optional startup registration: `HKCU\Software\Microsoft\Windows\CurrentVersion\Run\EyeBreakReminder`.
- Preferences and timer state: `%LOCALAPPDATA%\EyeBreakReminder\settings.ini` and `timer.dat`.
- Break history and statistics: `%LOCALAPPDATA%\EyeBreakReminder\history.dat`.
- Update staging and recovery copies: `%LOCALAPPDATA%\EyeBreakReminder\updates\<random-guid>`.

The portable ZIP contains the same standalone executable as `EyeBreakReminder.exe`. A process launched from the registered install directory uses the installed-package path; an executable without matching per-user installation registration uses the portable path. Both formats use the existing per-user data store in production.

## Discovery and authentication

The app discovers the latest stable release from the official GitHub repository using WinHTTP. The response must be HTTP 200, within the size limit, stable and non-draft, semantically newer than the installed version, and bound to the exact official repository URL.

Before an update is offered or downloaded, production retrieves the manifest and detached signature from the canonical GitHub release path. The parser accepts only canonical schema-1 JSON with fixed property/asset order and rejects duplicate, unknown, missing, malformed, or noncanonical fields. Windows CNG verifies the 64-byte raw P1363 ECDSA P-256/SHA-256 signature against the public key embedded in `src/update_trust.hpp`.

The manifest binds application and repository identities, version/tag, stable channel, x64 architecture, key ID, issue/expiry times, and exactly two role-bound payloads. Installed applications select only `EyeBreakReminder-Setup-x64.exe`; portable applications select only `EyeBreakReminder.exe`. GitHub digests are an additional consistency check and cannot override signature failure.

After download, the application verifies the signed size and digest, then writes the exact signed metadata to its private staging directory. The coordinator reparses and re-verifies the signature, selected asset role, version, payload size, and digest immediately before invoking the installer or replacing the portable executable. Production always uses the embedded root. The test-only staging key path and local metadata/asset/data overrides exist only in `EYEBREAK_TEST_BUILD`.

## User flow

1. A manual or optional daily update check runs off the UI thread. Automatic checking and downloading default off.
2. If an eye break is active, update dialogs and automatic downloads wait until it ends. A manual break dismissal can queue the pending update promptly; an already approved download continues in the background.
3. The native update dialog shows installed/latest versions, release notes, and known size. Preserve Settings is selected by default. “Remind Me Later” dismisses that version for the current process.
4. Download and install progress displays actual bytes, percentage, and downloading/verifying/ready phases. Cancel removes the incomplete staging file and keeps the current app unchanged.
5. Clean Install requires separate confirmation. Its history/statistics deletion checkbox defaults unchecked. Data cleanup occurs only after the new executable is installed and verified.
6. The app copies itself to the transaction coordinator, writes the recovery record, then exits through its normal shutdown path. The coordinator waits and does not force-kill the app.
7. Installed updates run the verified per-user NSIS setup. Portable updates stage and atomically replace only `EyeBreakReminder.exe`; unrelated files remain untouched.
8. The coordinator checks the resulting executable version and digest, applies the selected data policy, starts the new app, and waits for startup confirmation before completing the transaction.

The native update dialog exposes accessible control names and a determinate progress value tied to downloaded bytes. The coordinator has accessible phase text and a native UI Automation close action.

## Failure recovery

The transaction record is restricted to the expected staging directory, exact target executable, current Windows profile, and supported asset names. It records the prior executable digest, signed payload identity, known data/installer-file backup masks, backup digests, selected data policy, and journal phase.

Before replacement, the coordinator saves the old executable, the three recognized data files, and present NSIS-owned files. It verifies both original and backup bytes before recording them. During recovery, it validates every required backup and staged restore copy before changing any live data file. A missing or corrupted later backup cannot partially restore earlier settings/history files.

Installer errors, version/digest mismatches, data-policy errors, or missing startup confirmation attempt to restore the previous executable, recognized data, installed-version registration, and prior startup setting. The old app is restarted only after its version and digest are checked. If recovery cannot complete, the coordinator preserves the remaining backup and recovery registration and reports the failure.

A RunOnce recovery helper checks the durable journal after an unexpected restart. Before installation it clears unused recovery state; during or after installation before the `complete` phase it restores the prior executable/data. A `complete` journal is not rolled back. This is transaction recovery, not a user-facing downgrade feature. Older signed manifests are not a downgrade bypass.

## Clean installation and uninstall

Clean Install deletes only the known settings file and transient timer checkpoint. History remains unless the user separately chooses to delete it. App-owned startup state is reset. Unknown files in application data are not recursively removed.

Interactive uninstall offers Keep or Remove settings/history. Silent uninstall keeps preferences/history and removes only the transient timer checkpoint. Application files, shortcuts, and registration are removed using the existing per-user NSIS identity; the shared Local AppData folder is never recursively deleted.

## Bootstrap and release packaging

The first v1.4.0 installation must be obtained by a trusted manual process because the embedded public key cannot authenticate the installer that first carries it. Later stable releases must publish the canonical setup and standalone executable asset names and signed update metadata. The updater downloads the standalone executable rather than the portable ZIP so it does not overwrite unrelated files in a portable folder.

The finalizer validates and retains the signed seven-file candidate. After independent artifact verification, its production-transaction job tests the authentic v1.4.0 signature against an isolated v1.3.0 baseline; the baseline has test-only feed/data hooks but no test public key, so verification uses the embedded production root. It rejects a disposable test-key signature, installs the exact candidate setup, and verifies relaunch and user-data preservation. Exact results are recorded in the final reports and acceptance matrix.
