## Existing storage and install layout

- Per-user NSIS installation: `%LOCALAPPDATA%\Programs\EyeBreakReminder`.
- Per-user Windows registration: `HKCU\Software\EyeBreakReminder` and `HKCU\Software\Microsoft\Windows\CurrentVersion\Uninstall\EyeBreakReminder`.
- Startup registration, when explicitly enabled: `HKCU\Software\Microsoft\Windows\CurrentVersion\Run\EyeBreakReminder`.
- Preferences and timer state: `%LOCALAPPDATA%\EyeBreakReminder\settings.ini` and `timer.dat`.
- Break history/statistics: `%LOCALAPPDATA%\EyeBreakReminder\history.dat`.
- Update staging and recovery copies: `%LOCALAPPDATA%\EyeBreakReminder\updates\<random-guid>`.

The portable ZIP contains the same standalone executable distributed as `EyeBreakReminder.exe`. The app treats a process launched from the registered install directory as installed; an executable without that matching per-user installation registration uses the portable path. Both formats use the existing per-user data store in production, so moving the portable EXE does not move or erase settings/history.

## Discovery and selection

The app calls GitHub's public `GET /repos/REMEDIOSSAMUEL/EYE-BREAK-REMINDER/releases/latest` API endpoint over WinHTTP. The response must be HTTP 200, within the 1 MiB cap, stable, non-draft, semantically newer, and have the exact official repository release URL. Numeric semantic-version comparison avoids lexical ordering and rejects malformed tags and downgrades.

WinHTTP sessions are reused from a bounded process-level cache keyed by access mode, proxy, and timeout profile. Connections and requests remain per-operation RAII handles. This avoids native handle growth seen with repeated resolver failures while preserving separate bounded timeout policies for metadata checks and large payload downloads. The fixed session set remains until process exit so an update worker detached during window teardown cannot race a session-pool destructor; Windows releases it at exit.

Before it offers or downloads a discovered release, the production updater fetches the two metadata assets over validated HTTPS from the exact official release URL. It parses the exact canonical schema-1 JSON and verifies the detached 64-byte P1363 ECDSA P-256/SHA-256 signature with Windows CNG and the public key embedded in `src/update_trust.hpp`. The signed metadata binds the application and repository identities, release tag/version, stable channel, x64 architecture, issue/expiry times, and exactly one installed setup asset plus one portable-update executable with role, filename, architecture, size and SHA-256. GitHub's digest, if present, must agree with the signed digest. No unsigned fallback is available.

The signed manifest and signature are atomically copied into the private staging directory. The coordinator re-parses and re-verifies them before making backups, then rechecks signed metadata, the selected asset binding, payload size and digest immediately before launching the installer or replacing the portable executable. The test-only staging public key exists only in `EYEBREAK_TEST_BUILD`; production always uses the embedded root. The current root is deliberately unprovisioned and the app rejects all updates until the owner embeds the public half of a protected production key.

Installed copies select exactly the signed `EyeBreakReminder-Setup-x64.exe`; portable copies select exactly the signed `EyeBreakReminder.exe`. The asset URL must be the canonical official release-download URL for the tag and name, and the expected size and digest come from the authenticated manifest. The installed flow also validates the installed executable against the signed standalone `EyeBreakReminder.exe` identity after NSIS finishes.

## User flow

1. A manual or optional daily background check runs off the UI thread. Automatic checking and automatic downloading both default off.
2. If an eye break is active, update dialogs and automatic downloads wait until it ends. Ending a break manually queues the pending update prompt immediately, without waiting for the next timer tick. A user-approved download that is already running continues in the background if a break begins; its progress window is hidden until the break ends.
3. The native update dialog shows the installed version, stable version, release notes, and known size. Preserve Settings is selected by default. Remind Me Later dismisses that version for the current process.
4. Download & Install shows real bytes, total size, percentage, and Downloading/Verifying/Ready to install phases. Cancel removes the incomplete staging file and leaves the installed app alone.
5. Clean Install requires a second confirmation. Its separate history/statistics checkbox defaults unchecked. Preferences/history are backed up before installation; cleanup occurs only after the new executable is installed and verified.
6. The app copies itself to a separate coordinator, records the transaction, then exits through its normal shutdown path. The coordinator waits for the original process and never force-kills it.
7. Installed copies launch the verified per-user NSIS setup in silent upgrade mode. Portable copies copy the verified standalone EXE to a same-folder temporary filename and atomically replace only `EyeBreakReminder.exe`; unrelated portable-folder contents are untouched.
8. The coordinator checks the executable's version and published SHA-256, applies the chosen data policy, starts the new app, and waits for its startup-confirmation event. Only then is the transaction marked complete.

The coordinator is a native Win32 window. Its phase text and indeterminate installation indicator have accessible names, and the final Close button exposes a native UI Automation Invoke pattern. The download dialog uses a determinate, named progress control with an accessible 0–1000 RangeValue tied to actual downloaded bytes.

The test build can use a local metadata and asset fixture. That path is compiled only into `EYEBREAK_TEST_BUILD`; production builds always use GitHub and its HTTPS redirects.

## Failure recovery

The transaction record is restricted to the expected staging directory, exact target executable, current Windows profile and supported asset names. It records the prior app digest, downloaded size/digests, data and installer-file backup masks, SHA-256 digests for each present backup, selected data policy and journal phase. Before replacing files, the coordinator saves the old executable, the three known data files, and the installed NSIS-owned `Uninstall.exe`, `README.md`, `PRIVACY.md` and `VERIFICATION.md` files that are present. It hashes each original and copied backup before saving the journal. During recovery, it validates every required backup and its staged restore copy before replacing or deleting any live data file; a corrupt later backup therefore cannot cause an earlier settings file to be partially restored. The exact previous file set is restored if setup fails. It also registers an HKCU RunOnce recovery helper before install begins.

Installer errors, mismatched versions/digests, clean-policy errors and missing startup confirmation attempt to restore the old executable, existing data, installed-version registration and prior startup setting. The old app is restarted only after its prior version is checked. If a locked process or another recovery error prevents restoration, the coordinator keeps the backup and recovery registration and reports that recovery did not complete. It does not claim success.

After an unexpected restart, the RunOnce helper reads the durable phase. Before installation, it clears the unused recovery entry. During or after installation but before the `complete` phase, it verifies and restores the prior executable/data. A `complete` journal is not rolled back. Recovery failure preserves the recovery directory for another attempt or manual support.

This is a one-version transaction rollback for failures in an update. It is not a user-facing “revert to previous version” feature. The successful update staging copy is removed after the coordinator has closed and the recovery entry is absent.

## Clean install and uninstall

Clean Install deletes only `settings.ini` and the transient `timer.dat`; `history.dat` remains unless the user separately selects its removal. Startup registration owned by this app is also reset. Unknown files in the application-data directory are not recursively deleted.

Interactive Windows uninstall offers Keep or Remove settings/history. Silent uninstall deterministically keeps preferences/history and removes only the transient timer checkpoint. App files, shortcuts and registry entries are removed using the existing per-user NSIS identity. Uninstall never recursively removes the shared Local AppData folder.

## Initial transition and release packaging

Published v1.3.0 has only a check-and-open-release-page flow. It cannot acquire the v1.4.0 updater before v1.4.0 is installed. The one-time v1.3.0 to v1.4.0 transition is the normal v1.4.0 per-user installer upgrade; thereafter the integrated flow can install future stable releases.

Future updater-compatible GitHub releases must publish the canonical `EyeBreakReminder.exe` and `EyeBreakReminder-Setup-x64.exe` asset names with GitHub SHA-256 asset digests. The portable ZIP, source ZIP, and manifest remain part of the five-file release contract, but the updater does not download a portable ZIP because updating only the published executable avoids overwriting unrelated files in a user's portable directory.
