## Final repair and recovery campaign

This section records the corrected source and fixture evidence collected before final signing. Artifact 15007651099 is the historical reproduction candidate.

| Pretest conditions | Expected behavior |
|---|---|
| Installed app without recovery pending, including a missing, corrupt, or truncated image | Same-directory setup restores the exact fixture image, preserves preferences, history and eligible timer checkpoint, and leaves no pending rollback. A genuine fresh installation clears a stale timer checkpoint. |
| Owned pending command, repeated setup, malformed or foreign value in the reserved name, missing value with interrupted journal, or malformed readable journal | External setup defers before closing the app or mutating installed and recovery files. It preserves both the reserved value and unrelated values. |
| Missing or corrupt helper, or completed partial rollback awaiting retry | Setup defers. It neither reconstructs nor executes a helper from local state. |
| Live coordinator launching the signed fixture in its own application stage | Managed setup proceeds and leaves the original authenticated rollback route functional. Manual setup launched from the same path is deferred. |
| Fresh recovery with a missing or corrupt executable, declared installed file or profile backup | Reject before replacing the executable. Preserve surviving backups and current data. A locked destination can still interrupt a legitimate rollback, and an ordinary retry remains available after unlocking. |
| Fresh recovery with different live settings or history, or a conflicting live file without recorded backup | Defer rather than replace or delete the conflicting file. Existing copies and recovery evidence stay available. |
| Fresh recovery with intact backups and absent or byte-identical live settings/history | Restore the prior application and applicable data. The completed Clean Install path remains terminal. Repeated recovery and repair after resolution retain coherent versions and the selected data policy. |

A fresh installation still drops a stale checkpoint. The regression uses a separately compiled installer that packages the exact original EXE. Shipping the installer correction requires a replacement setup and production manifest signature because the existing signed manifest binds the original setup hash. ## Recovery test boundary

The hosted run stages the authentic 1.4.0 payload and manifest for a lower-version baseline. The real published 1.3.0 setup supplies the installed files. The disposable baseline executable is compiled from reviewed updater source with 1.3.0 resource version so the relaunch can acknowledge the recovery protocol. Published 1.3.0 predates that protocol. The test starts the exact v1.4.0 coordinator, which validates the production signature and creates its own backups, recovery journal and RunOnce value. The staging and invocation exercise the coordinator entry point directly.

Debugger process creation events identified two boundaries: exact installer creation before installer instructions, and exact successor creation after verified replacement and clean policy but before successor instructions. An individual installer write in progress was not interrupted. The recovery process started in a separate hosted step from the exact captured 250-character HKCU RunOnce command.

All three recovery jobs in [run 45608474782](https://github.com/REMEDIOSSAMUEL/EYE-BREAK-REMINDER/actions/runs/45608474782) passed, including each runner's seven-file and signature verification. The run as a whole failed because the separate NSIS regression step could not resolve an icon from a relative source path and never executed the regression. Independent reviewers opened and rehashed each recovery report.

Both post-replacement jobs locked the real uninstaller. Exact recovery restored the executable but stopped at the locked owned file, retaining data backups and retry state. After that helper was terminated and the lock released, a fresh invocation restored all prior owned files, settings, history, version and startup registration. The unrelated file was unchanged. The restored application relaunched and its timer advanced. Replaying the exact command again while the restored app was up had no effect. The confirmation-capable baseline handled cleanup after the harness modeled Windows deleting the entry. Exact v1.4.0 startup cleanup in the successful forward direction is already covered by [finalizer transaction artifact 15007776608](https://github.com/REMEDIOSSAMUEL/EYE-BREAK-REMINDER/actions/runs/45582714164/artifacts/15007776608).

Manual reinstall alone is therefore insufficient when a genuine rollback is still pending. Setup preserves the journal and backups, which is necessary to retain recovery options. A version equality check or unconditional RunOnce deletion would remove rollback from genuinely interrupted transactions. Preserve the recovery folder and use the app's documented recovery route or contact support before relying on a reinstall. Reinstall can restore installed bytes and cannot recreate missing user files by itself.

The supported scope for ordinary same-directory reinstall is application file repair when there is no pending recovery. With pending recovery, keep the saved transaction and follow the supported recovery route before relying on a reinstall. If the helper or executable backup is unavailable, retain the folder for support. Remaining backup files may be useful, but this campaign established no supported automated way to restore user data from those incomplete transactions.
