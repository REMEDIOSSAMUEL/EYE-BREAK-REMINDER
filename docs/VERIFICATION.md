# Verification — Windows x64 release 1.0.4 (earlier releases cross-compiled from Linux)

This deliverable uses **C++17 / native Win32**, replacing the earlier WinUI/.NET implementation at the user's request to compile from Linux.

- Application: compiled with MinGW-w64 GCC 13-win32, x64 Windows GUI subsystem, static GCC/C++ runtime linkage. Build treats compiler warnings as errors.
- Automated core tests: **58 assertions executed successfully on Linux**, covering work/break timing, pause/resume/reset, snooze, alarm rules, duplicate prevention, sleep/wake, nested lock/sleep, restart recovery, settings/state/history serialization and corruption, statistics and history retention. These are actual C++ tests of the core linked into the Windows application.
- Installer: generated with Linux NSIS 3.09. The GUI bootstrap is x86; installation is restricted to native Windows 11 x64 and deploys the x64 GUI application.
- Binary verification: PE architecture/subsystem and security flags, imported DLLs, embedded manifest/version/icon/sound resources, and signing-directory status are checked by `scripts/verify.py`. The source and portable archives and SHA-256 manifest are checked after packaging.
- Signing: **unsigned**. No certificate or publisher identity was supplied. No Windows certificate validation or security setting is changed.
- Windows 11 runtime: **unavailable**. No manual Windows application launch, installation, uninstall, audio, tray, notification, DPI, accessibility or lifecycle testing is claimed. Wine is not installed and is not counted as Windows 11 testing.

Important limits: native Win32 controls provide a different presentation from WinUI 3. App surfaces/title bars support theme choices; buttons/checkboxes use themed custom drawing while dropdowns/sliders/scrollbars retain native rendering; visual fidelity, native control contrast, text scaling and per-monitor layouts remain runtime-unverified. Notifications are Shell balloons with click-to-open, not actionable toasts. All-display reminders are omitted. There is no supplied source licence or copyright/publisher identity. History totals are bounded to retained records.

Run `docs/WINDOWS-TESTING.md` on a real Windows 11 x64 system before calling this a production-verified release. The source includes the exact Linux build/packaging commands, tests and verification script.

## Settings visibility fix (1.0.1)

The user supplied a Windows screenshot showing an empty Settings page except for the scrollbar and spin arrows. Inspection found that shared control creation omitted `WS_VISIBLE`, while page switching deliberately left the Settings children to inherit visibility from their parent. Version 1.0.1 creates these children visibly and continues to hide/show the parent pane when switching pages. Number fields now keep explicit references to their spin controls for layout, and the pane clips child drawing during background erasure. Version metadata distinguishes this rebuild from 1.0.0. The core and binary/package checks were rerun after this change. Visual confirmation of this fix on Windows is still pending.

## Tray-menu layering fix (1.0.2)

The user supplied a screenshot showing the native tray context menu partially covered by the Windows hidden-icons flyout. Version 1.0.2 uses a dedicated zero-size tool window as the foreground menu owner, makes that owner temporarily topmost while tracking the menu, and removes that status afterward. The main application is never made topmost. The icon bounds are read with `Shell_NotifyIconGetRect` before activating the menu owner, and `TrackPopupMenuEx` positions the menu above the icon with a padded exclusion rectangle. Version-4 tray callback coordinates support mouse and keyboard invocation. Focus returns to the tray only for cancellation and commands that keep the app hidden. Selecting Settings now keeps the Settings window in the foreground even during a break. Build/core and binary/package checks were rerun. Windows runtime confirmation of this fix remains pending.

## Reinstall recovery and visual polish (1.0.3)

The earlier uninstaller intentionally preserved all application data, including `timer.dat`. Version 1.0.3 deletes that checkpoint during uninstall, and on a fresh install before copying the application. Direct upgrades preserve it. Preferences and history are retained. Turning off resume-on-reopen skips restoration without treating that choice as corrupt data. Two additional core assertions cover opt-out of restoration and the resulting fresh work state. Windows install/uninstall execution is still pending.

Native buttons and checkboxes now use common-controls custom drawing, keeping native input and accessibility behavior. Rounded push buttons, visible selected navigation, blue primary actions, softer palettes, clearer settings headings, compact label spacing and padded number fields are implemented. Native rendering is retained for buttons in high contrast. Visual/DPI/accessibility checks on Windows are still pending. Source layout, contribution and manual release documentation were prepared. Repository publication is separate from Windows runtime verification and uses the owner's signed-in GitHub account. Publishing source and release assets does not establish Windows runtime correctness.

### Blank time fields after scrolling (found in manual acceptance testing)

Observed by a person during the Group 1 manual checks on commit a744648: after applying the Weekdays preset and scrolling Settings → Schedule, the time fields showed empty boxes (only a field that had keyboard focus still showed its time). The scripted runs had missed it because their captures used `PrintWindow`, which makes the window repaint itself first.

Investigation, on the running instance and on a test instance: every field still held its correct text (`WM_GETTEXT` returned 09:00/17:00 for all days) and `settings.ini` held the correct periods, so no data was lost. Measuring the pixels actually displayed reproduced it every time on the unfixed build: before scrolling all visible fields showed their times; after scrolling down with the mouse wheel or the scroll bar all 14 visible fields were empty, and 8 were still empty after scrolling back up. It happened equally on a fresh start without any preset or rebuild.

Cause: the edit-control subclass (introduced with the 1.0.6 redesign, unchanged since) paints its own 1 px frame in `WM_NCPAINT` through `GetWindowDC`, and filled the whole window rectangle, including the client area that holds the text, with the field colour. Layout changes move controls with `SWP_NOCOPYBITS` and repaint them completely, but scrolling moves them with copied bits: Windows then repaints the frame (`WM_NCPAINT`) but treats the copied client area as valid and sends no `WM_PAINT`, so the frame painter erased the text and nothing redrew it. Focus changes force a full redraw, which is why a focused field still showed its value. In 1.0.6 only the Intervals number fields used this code and that section never scrolls; the Schedule section is the first scrolling page with such fields.

Correction (`src/app.cpp`, edit subclass `WM_NCPAINT`): the client rectangle is excluded from the clip region before the frame is filled and outlined. Nothing else changed: no extra invalidation, the cheaper copy-bits scrolling is kept, and no other control is affected.

Verification on Windows 11 build 26300 at 150% (scripted; the test windows were kept behind other windows and never activated, and the measurement copied the window's own surface without making it repaint):

- The measurement was first shown to detect the defect: on the unfixed build (rebuilt from a744648, identical to the earlier release executable apart from its link time) it reported 14 blank fields after scrolling down and 8 after scrolling up; on the fixed build 0 and 0. The two captures were inspected by eye and match those numbers.
- 43 of 43 checks on the fixed build: five wheel down/up cycles, a mid-animation frame, scroll-bar line steps, bottom and top, Tab focus scrolling through all days, light and dark themes, resizing to 520 and 900 logical px while scrolled, ticking and unticking a day, Add period and Remove period (which rebuild the controls), switching to Alarm and back, the Intervals number fields, restart, and 96 DPI (app run DPI-unaware). ### Initial Timer progress ring implementation (superseded; 2026-11-03)

This section preserves the verification history for the first ring implementation. Its child-control ring painting and its pass claims below were superseded after the owner reported Dark-mode white rectangles, visible jitter/flicker and countdown stalling during live resize. The current implementation and correction results are recorded in the next section.

**Root cause:** the earlier 1.0.6 note above records that the ring had small gaps where its two text labels masked it. Source inspection confirmed the cause: the main window uses `WS_CLIPCHILDREN`; the countdown and caption are full-width native `STATIC` children crossing the ring; and the shared `WM_CTLCOLORSTATIC` handler returned an opaque background brush. The parent's backbuffer is clipped out of the child areas, then each static painted over those ring sections. The full-circle arc change alone did not fix this.

**Implementation:** the Timer page draws a complete background ellipse. A shared helper draws intermediate active progress clockwise from 12 o'clock, with a GDI+ sweep of 360 × elapsed progress, and uses a closed ellipse at exactly 100% to avoid angle wraparound. `Snapshot::progress()` remains the source of clamped 0–1 elapsed progress. To keep the native accessible text controls and their existing layout, their `WM_CTLCOLORSTATIC` paint now fills the child background with the current theme color, draws the same DPI-scaled ring using the shared geometry translated to the child's HDC, sets transparent text background and returns `NULL_BRUSH`. One progress sample is captured per UI update and reused by both parent and child drawing. The existing label controls are invalidated on the existing render cadence so their ring portions stay synchronized. The child subclass suppresses erase-only paints; its other messages pass through unchanged. No timer, schedule or persistence logic changed.

**Independent review and self-correction:** a separate reviewer first found the ring math sound but left the root cause uncertain; that version had not fixed the label mask. A fresh adversarial follow-up inspected the styles, bounds and color handler, identified the opaque-child defect and rejected the ellipse-only change as insufficient. **Source-confirmed Dark-mode painting defect:** the main window has `WS_CLIPCHILDREN`, so its buffered paint is clipped out of the native countdown/caption `STATIC` client rectangles. The earlier ring workaround suppressed each label's `WM_ERASEBKGND`, set transparent text background, manually painted into its control DC, and returned `NULL_BRUSH` from `WM_CTLCOLORSTATIC`. Win32 defines that return value as the brush used to paint a static control background; the null brush did not provide the active theme brush. This left child background rendering dependent on the manually composed pixels and default static behavior, which is a fragile path for themed opaque child windows. The exact source of the owner's white pixels was not observable without a live window, so the pixel-level diagnosis remains unconfirmed. See Microsoft's [`WM_CTLCOLORSTATIC`](https://learn.microsoft.com/en-us/windows/win32/controls/wm-ctlcolorstatic) and [child-window update/painting](https://learn.microsoft.com/en-us/windows/win32/gdi/child-window-update-region) documentation.

**Source-confirmed paint instability and likely jitter mechanism:** the earlier code drew the ring in the parent backbuffer and then drew it again in each of two child control HDCs. The engine was not stopped: `Engine::snapshot()` derives remaining time from the monotonic clock and the Windows implementation uses `QueryPerformanceCounter`; the deadline worker remained responsible for actual timer deadlines.
