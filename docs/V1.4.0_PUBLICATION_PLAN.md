## Signed-manifest expiry and renewal

1. Confirm the target tag, candidate and current UTC. Renew an unpublished candidate only if the existing window is unsuitable. For an expired published offer, default to retaining the release and providing a trusted manual path or a separately authorized newer signed release. Renewing the same version can only help compatible clients below that version. [Expiry behavior](UPDATE_SIGNING_AND_KEY_MANAGEMENT.md#how-manifest-expiry-affects-users)
2. Get explicit approval for production signing. Preserve the original seven-file set, sizes and SHA-256 hashes, including the original signed pair and signing evidence. Verify the original pair's cryptographic signature even if it is expired. Confirm the frozen source and compare the five unchanged files (four payloads and their checksum file) against the independent baseline. Check both signed payload sizes and hashes. If bytes differ, stop and reconcile them before signing.
3. In a new private staging directory, use the existing `scripts/update_signing.py sign` command in the signing guide. Pass the same stable `X.Y.Z` to `--version`, the approved UTC deadline to `--expires-at`, and the exact verified setup and portable executable to `--installer` and `--portable`. Point both output arguments at fresh canonical filenames in that staging directory. Use the existing production PEMs for `p256-0aff97759ea95258`. The tool sets the current issue time, limits validity to 90 days, and prompts locally for the private PEM passphrase. The intended changes within the manifest are only `issued_at` and `expires_at`. No payload rebuild is needed. [Exact PowerShell arguments](UPDATE_SIGNING_AND_KEY_MANAGEMENT.md#sign-and-verify-a-release)
4. In independent staging, compare old and new parsed fields except the two timestamps. Run `update_signing.py verify` and `verify-embedded` on the fresh pair, then use the Windows CNG production verifier with the actual tag, a compatible older version and current UTC. The OpenSSL-based commands verify signature and schema. Check the live time window and both payload bindings separately. Rehash all seven final files against the baseline plus the two new metadata hashes and verify that the four-payload checksum file still matches. Save authorization, UTC window, source and candidate identity, both sets of metadata hashes and the independent verification receipt.
5. For an unpublished release, stage the verified pair with all five unchanged files in a single draft. Confirm the complete draft contents before making it discoverable. For an already public release, obtain separate explicit approval before altering assets. GitHub immutable releases prohibit replacement. Where edits are permitted, GitHub exposes separate asset operations, so a pair replacement can briefly cause a failed update check. Prefer a successor published from a fully verified draft when uninterrupted discovery matters. [GitHub release management](https://docs.github.com/en/repositories/releasing-projects-on-github/managing-releases-in-a-repository) · [GitHub release asset operations](https://docs.github.com/en/rest/releases/assets)
6. If the owner approves an exceptional in-place edit on a mutable release and accepts the brief interruption, preflight access, preserve the old pair under its hashes, and stage the verified new pair before the window. Replace only the two canonical metadata assets back-to-back in one supervised session. Independently download both as a public client, check exact hashes, signature, payload bindings, freshness and discovery before declaring success. A mixed or missing pair must fail closed. If verification fails, stop and escalate to the owner. Restore only an independently verified still-valid original pair under an approved fallback plan, or keep the offer unavailable pending an approved correction. Preserve both generations and never relax signature checks to complete publication.

## Future release checklist

1. **Branch and scope.** Start a feature branch from verified `origin/main`. Review reported defects, identify changed behavior and define the smallest relevant regression set. Keep unfinished experiments out of production inputs.
2. **Test changes.** Run required CI and focused tests for affected app, packaging, installed and portable paths. Verify manifest authentication, rejection paths, hash binding, and recovery where affected. Run targeted resource stability tests when the changes could affect long-running behavior. 5. **Merge and tag.** Wait for owner publication approval, required CI and reviews, and merge through protected main. Compare the merged production inputs with the frozen built tree. Stop on unexplained differences. Create the approved tag on the verified merge commit and record how the tag, frozen source, Source ZIP, and exact binaries relate.

From independent public downloads check all seven hashes, signature, freshness, bound payload sizes and hashes, and correct release discovery. Preserve all prior releases and tags.
7. **Verify the live experience.** In disposable Windows test profiles, use a compatible older production client to discover the real published successor, accept the signed offer, and verify installed and portable update behavior as applicable. Confirm relaunch and expected data preservation. Confirm the new version reports up to date. Exercise applicable interruption and recovery paths in an isolated setup pointed at the exact candidate. Document any fixture or environmental limitation separately from tested production behavior.
8. **Close out.** Record the public URL, tag and merge, protected CI, frozen source, artifact and hashes, signing identity, manifest window, live update and recovery results, prior-release preservation and outstanding limitations. Secure durable evidence, note Actions expiry and set the next manual maintenance review. [Maintenance checks](UPDATE_SIGNING_AND_KEY_MANAGEMENT.md#maintenance-checks-and-approvals)
